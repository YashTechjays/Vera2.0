RBAC DEMO RUNBOOK — PR #58 (feat/rbac)
========================================

BEFORE THE DEMO (5 min, do this alone)
--------------------------------------
1. Backend terminal (vera-backend) — verify the DB FIRST:
     echo $env:VERA_DATABASE_URL        -> must say ...vera_rbac_demo
   If not:
     $env:VERA_DATABASE_URL = "postgresql+asyncpg://vera:vera@localhost:5432/vera_rbac_demo"; just api

2. Frontend terminal (vera-frontend):
     npm run dev

3. Logins (tenant: vera-health-example, password: dev-password-change-me):
   - Window A (normal browser):  admin@veratechsolutions.example   (presenter)
   - Window B (incognito):       va2@test.example                  (test user)

4. Sanity click: Settings opens in Window A -> good to go.


THE DEMO (10 min)
-----------------

SCENE 1 — "Roles are real and take effect instantly"
  1. A: Settings -> Roles & Permissions.
     Point out system roles — SUPER_ADMIN does NOT appear.
     SAY: "Platform roles are filtered server-side, keyed on permission, not name."
  2. A: Create role "Read-Only Viewer" -> tick only forms:read -> Save.
  3. A: User Roles card -> select va2 -> assign "Read-Only Viewer"
     -> remove TENANT_ADMIN from va2.
  4. B: log out, log back in as va2
     -> Settings gone, Users refuses, Data Management still readable.
     SAY: "Role changes invalidate the permission cache immediately —
           no waiting, no re-deploy."

SCENE 2 — "Guided, safe deletion"
  5. A: try Delete on "Read-Only Viewer" -> blocked;
     dialog shows "Held by 1 user", holder listed BY NAME ONLY.
     SAY: "No cascade — each removal is deliberate and audited.
           Names only; emails stay behind users:read."
  6. Click Remove on va2 inside the dialog -> then Delete -> role gone.
  7. B: refresh — va2 has no roles. (Restore later: assign TENANT_ADMIN back.)

SCENE 3 — "You can't shoot yourself"
  8. A: User Roles card -> select yourself -> try removing your own TENANT_ADMIN
     -> refused: "cannot remove your own last role-management role."
     SAY: "Self-lockout guard — a tenant can never strand itself with no admin."

SCENE 4 — "Everything is evidence" (compliance close)
  9. Run live in a terminal:
     docker compose exec postgres psql -U vera -d vera_rbac_demo -c "SELECT event_type, metadata->>'role_id' AS role, created_at FROM auth_audit_log WHERE event_type LIKE 'role%' ORDER BY created_at DESC LIMIT 8;"
     Every click from scenes 1-3 is there: role_created, role_grant,
     role_revoke, role_updated, role_deleted.
     SAY: "The last two event types are what the rebased migration enables."

SCENE 5 — Close on his review
 10. SAY: "All 8 review comments are addressed — the migration is now one
           linear revision on dev's head."
     Proof if asked:  uv run alembic heads   -> one line (efa94eaaf3f9)


IF SOMETHING GOES SIDEWAYS MID-DEMO
-----------------------------------
- 500 on any save -> wrong DB: check echo $env:VERA_DATABASE_URL in the API
  terminal, restart with the demo URL, re-login in the browser.
- B doesn't lose access after a role change -> va2 must log out/in
  (sessions pick up roles at login).
- Roles messy from rehearsal -> delete demo roles in the UI, or rerun the
  idempotent seeds:
    VERA_DATABASE_URL=...vera_rbac_demo  uv run python scripts/seed.py
    (and again with SEED_ADMIN_EMAIL=va2@test.example)
