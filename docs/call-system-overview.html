Architecture Walkthrough

How Vera makes a call.

Vera is a HIPAA-regulated, multi-tenant AI voice platform. An AI agent phones insurance payers to verify patient benefits — while a human VA (virtual assistant) can listen in and take over. This document traces that call system end to end: how a call is born, the states it moves through, who built each piece, and exactly where today’s publish-to-others feature slots in.

01 Overview

The big picture in plain language, before any diagrams.

A Vera “call” is one AI agent phone conversation with an insurance payer. The system that runs it is split into two processes that never share memory. They stay in sync purely through a shared naming convention — there is no shared database session between them.

🎛️

Control plane FastAPI

The gateway. It owns Postgres, authenticates users, creates the LiveKit room, dispatches the agent worker, and mints the browser join token. It handles no audio.

🤖

Agent worker LiveKit

The voice brain. It joins the room and runs the cascade — Deepgram (speech-to-text) → Gemini (the LLM) → Cartesia (text-to-speech) — plus PHI redaction at the seams.

The one idea that ties it together

The room name IS the correlation key. One call = one LiveKit room, named call--<tenant_uuid>--<call_uuid>. Both processes derive the same trace/session id from that string without ever talking to each other. It is built and parsed only through vera_core.observability.correlation.

Two call paths exist today — this is the single most important thing to know

There are two different ways a call gets started, and they behave very differently. Keeping them straight is essential for planning the publish feature.

POST /api/v1/calls persistent

The real production flow. Writes a Call row to Postgres, runs the full CallStatus lifecycle, records an append-only event log, and exposes a supervisor-{user_id} join-token so humans can join a live call.

calls.py

POST /voice-lab/sessions ephemeral

A developer/QA harness. Creates a room and dials out but writes no DB rows and “never appears in Live Monitoring.” Deliberately decoupled from /calls. This is the path the current frontend actually uses.

voice_lab.py

Consequence for the UI

The Live Monitoring page — the call list, the “Visible To All” toggle, the Intervene and View-Live modals — is currently driven by mock data (src/lib/mock-data.ts), not the persistent /calls API. The backend has the machinery for real multi-call supervision; the frontend hasn’t been wired to it yet.

Initiation, step by step (the persistent /calls path)

Request arrives  calls.py:57

A StartCallRequest {form_id} hits POST /api/v1/calls. It passes the standard chain: authenticate → require("calls:read") → tenant-scoped session (RLS on).

Validate the patient form  calls.py:64

Looks up the PatientForm. Row-level security already constrains the query to the caller’s tenant, so a missing form is a clean 404.

Create the Call row  calls.py:70

Inserts Call(tenant_id, form_id, current_status=INITIATED) and flushes to get the UUIDv7 primary key. The tenant is taken from the verified identity — never from the request.

Derive the room name  calls.py:74

room_name_for_call(tenant_id, call.id) → call--<tenant>--<call>. This is the single string that lets the worker correlate everything with zero shared state.

Create room + dispatch the agent  calls.py:81

livekit.create_call_room(...) creates the LiveKit room and explicitly dispatches the vera-agent worker into it. Non-PHI persona config rides along as room metadata.

Queue the form & log the event  calls.py:82

The form flips to IN_QUEUE, and an append-only CallEvent(STATUS, "initiated") row is written — the beginning of the audit trail. Returns a CallSummary.

How a human joins a live call today

GET /calls/:id/join-token mints a LiveKit token under the identity supervisor-{user_id} scoped to that one room. That is the existing hook the “intervene” feature will build on. The worker recognizes identity prefixes: caller- (browser mic), monitor- (listen-only), phone-callee (the payer), and supervisor-.

03 State lifecycle

The states a call moves through — and where the new visibility states will overlay.

A call’s status lives in Call.current_status, a maintained enum guarded by a database CHECK constraint (the v1 fix for free-text status drift). Every transition also appends a CallEvent row, so the history is never lost. There are ten states; six are “active” (shown in the live list) and four are terminal.

Notably absent

There is no published / visibility column today, and the list endpoint (calls.py:138) returns all active tenant calls with no per-VA filter — even though initiated_by_id exists and is already indexed for exactly this. The scoping slot is pre-cut; nothing fills it yet.

call_event

Append-only status/phase/health log. event_type, lowercase event_value, JSONB detail. The audit trail behind every transition.

call_lineage

retry_call_id → parent_call_id. Traces retry descent for partial re-runs of a call.

intervention_event exists, unused

In oversight.py: call_id, supervisor_id, type (flag/coach/whisper/takeover). No endpoints yet — a natural home for intervene actions.

06 What’s next — publish & intervene

Where today’s feature fits, what changes, and the open questions. (Plan only — no code yet.)

The feature in one sentence

When a VA initiates a concurrent call it is private to that VA by default; once the VA publishes it, other VAs in the tenant can view it, intervene, and operate on it.

The first decision: which call path is the substrate?

This is the fork in the road. “Concurrent calls” with ownership and visibility need persistence and a per-VA scope — things the ephemeral Voice Lab path deliberately does not have, but the persistent /calls path already does (initiated_by_id, the event log, the join-token). The realistic plan is to build on the persistent path and wire the frontend to it, replacing the mock Live Monitoring data.

Backend touchpoints

  • Add a visibility axis to Call — a published boolean (or a small visibility enum for future team_only states). Independent of current_status.
  • Set initiated_by_id on create (currently left null) so ownership exists to scope on.
  • New PATCH /calls/:id/publish — owner-only; flips the flag and appends a CallEvent for the audit trail.
  • Scope the list query (calls.py:138): initiated_by_id == me OR published, instead of all active calls.
  • Tighten authz — the code already flags that calls:read is a stopgap; publish/intervene likely want calls:write / a manage permission.
  • Intervene: give intervention_event (already modeled, unused) its first endpoints, gated so only published calls accept a foreign supervisor- join.

Frontend touchpoints

  • Introduce a real call-state slice in Redux (today call state is local component state in VoiceLab.tsx; only authSlice exists).
  • A Publish control in the active-session UI (SessionPanel actions) for the owning VA.
  • Point Live Monitoring at the real list API; replace the mock “Visible To All” toggle + mock-data.ts with server state.
  • Wire the existing Intervene / View Live modals to join-token so a second VA actually joins the room.
  • Support viewing another VA’s published call — today the browser hosts a single <LiveKitRoom> at a time.

Open questions & risks

① Substrate: extend Voice Lab, or wire up the persistent /calls path?
Voice Lab is explicitly ephemeral and stateless — it can’t carry ownership or cross-VA visibility. Confirm the intent is to move to (or converge on) the persistent path. This is the biggest scoping question and should be settled before code.
② What can an intervening VA actually do?
View-only vs. speak (barge-in) vs. take over the form vs. DTMF. The intervention_event.type enum hints at flag / coach / whisper / takeover — the product definition of each needs pinning down, and each has a different LiveKit permission + PHI implication.
③ Visibility is a PHI disclosure decision, not just a flag.
Publishing widens who can see a live call’s transcript (PHI). Per the backend guardrails, “who may see this” is a compliance call — publish likely needs its own audit event and possibly its own permission, not a silent query widening.
④ Can visibility live on Call, or does it need a real-time channel?
A DB flag answers “is it published?” but other VAs’ screens need to learn it changed. Decide between polling the list, an SSE/websocket signal, or a LiveKit data-channel event — the transcript already streams over SSE, so there’s a pattern to reuse.
⑤ Unpublish & ownership edges.
Can a VA un-publish while someone is intervening? Who owns a call after takeover? What happens to initiated_by_id on handoff? Define the ownership rules alongside the state machine.
